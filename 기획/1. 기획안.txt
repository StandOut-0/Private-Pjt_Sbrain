Second Brain 서비스 기획안 — 회의 아이디어 반영판
최종 정리: 2026-10-20

[적용 범위]
「4. 회의 - 아이디어 반영.txt」의 UI 개선 요구와 이후 화면 배치 결정을 통합한다.
이 문서는 목표 기능과 현재 구현 상태를 구분한다. 화면에 버튼·샘플 수치가 있다는 이유만으로 Backend 연결 완료로 보지 않는다.
9장 사이트맵, 10장 설명 및 14장 구현 기준을 최신 기준으로 사용한다.
기존 ASCII 와이어프레임은 초기 배치 참고도이며 최신 메뉴·상태 정의와 다르면 최신 설명을 적용한다.
이번 문서 정리는 Django 모델, 실제 DB, Agent 실행 코드를 변경하지 않는다.
2026-10-20 보완: 필수 화면 콘텐츠를 React로 이전하고 기존 Django URL·세션·권한·페이지별 초기 데이터 전달을 유지했다. 화면 구조·Bootstrap 기반 스타일·이미지 자산은 기존 디자인을 재사용한다. React 화면 전환과 Backend/DB·실제 Agent 연동은 별도 완료 조건으로 관리한다.




1. 프로젝트 개요
프로젝트명: Second Brain
한 줄 소개:또 다른 나를 만드는 개인 AI 업무 파트너 Agent 플랫폼

핵심 컨셉:
사용자가 하나의 AI와 대화하면, Second Brain의 Supervisor Agent가 사용자의 요청을 분석하고 필요한 전문 Agent를 조율한다.
전문 Agent들은 역할에 따라 기획, 자료조사, 데이터 처리, 디자인, Frontend/Backend 개발, AI 모델링, 결과 검증 등의 작업을 수행하며, 작업 과정에서 생성된 문서·코드·데이터·지식·결과물을 프로젝트 단위로 관리한다.

"사용자는 하나의 AI와 대화하지만, 내부에서는 여러 전문 Agent가 협업하여 프로젝트를 수행하는 개인 AI 업무 파트너"







2. 해결하고 싶은 문제
현재 생성형 AI를 활용하여 하나의 프로젝트를 수행하려면 사용자가 직접 여러 작업을 나누고, 각 작업에 적합한 도구와 AI를 선택해야 하는 경우가 많다.
예를 들어 사용자가 하나의 서비스를 만들기 위해서는 다음과 같은 과정을 직접 수행해야 한다.
아이디어 정리 - 요구사항 작성 - 자료 조사 - 데이터 수집 / 분석 - UI / 디자인 제작 - Frontend / Backend 개발 - AI 모델 적용 - 테스트 / 검증 - 문서화
이 과정에서 사용자는 작업마다 적절한 AI와 도구를 선택하고, 이전 작업의 결과를 다음 작업에 전달하며, 전체 결과를 직접 통합해야 한다.

Second Brain은 이러한 프로젝트 수행 과정을 하나의 서비스 안에서 연결한다.
사용자가 원하는 결과를 자연어로 입력하면 Supervisor Agent가 요청을 분석하고 필요한 작업으로 분해한 뒤, 각 작업에 적합한 전문 Agent를 선택하고 실행한다.

사용자 "신규 서비스를 기획하고 랜딩페이지까지 만들어줘."
          ↓
   Supervisor Agent
          ↓
     작업 분석 / 분해
          ↓
 ┌───────────────────────┐
 │ Planning              │ → 요구사항 / PRD
 │ Creative              │ → UI / 디자인 / 이미지
 │ Data                  │ → 자료 수집 / 분석
 │ Engineering           │ → Frontend / Backend
 │ AI                    │ → ML / DL / LLM
 │ Reflection            │ → 검증 / 개선
 └───────────────────────┘
          ↓
    결과 통합 / 검증
          ↓
   사용자에게 결과 제공

핵심 문제 → 해결 방식으로
작업을 직접 분해해야 함  →	Supervisor가 작업 분해
어떤 AI를 사용할지 직접 선택 →	전문 Agent가 역할별 작업 수행
작업 결과를 직접 전달 →	Agent 간 결과 공유
여러 도구를 오가야 함 →	하나의 Workspace에서 수행
결과물을 따로 관리 →	Project / Artifact로 관리
과거 문서를 다시 찾아야 함 →	Knowledge / Memory / RAG 활용
결과를 직접 검토해야 함 →	Reflection Agent를 통한 검증
프로젝트 진행 과정을 확인하기 어려움 →	Task / Agent Activity로 확인

중요한점.
Second Brain이 "사용자를 완전히 대체하는 AI"로 절대 정의하지않는다.
범위가 커져 커트라인 2달을 오바할 가능성이 커지기 때문.
사용자는 목표를 제시하고, Supervisor와 전문 Agent가 작업을 수행하며, 사용자는 과정과 결과를 확인하고 필요한 부분을 다시 지시하는 정도로 끝내야한다.
(다시 지시시에 작업량이 더 커짐으로 '이렇게할까요' 등의 되묻는 구조를 꼭 필수로 넣기로 한다. )









3. 핵심 사용자
Primary User: 혼자서 프로젝트를 기획하고 개발하는 개인 사용자
예:개발자, 기획자, 취업 준비생, 1인 창업자, 프리랜서
초기 버전에서는 혼자 프로젝트를 수행하는 개발자 / 기획자를 핵심 사용자로 설정한다.
사용자는 Second Brain을 통해 프로젝트의 아이디어를 입력하고, AI Agent와 함께 기획 → 설계 → 개발 → 검증 과정을 수행한다.

6. 서비스 핵심 가치
기존 AI: 질문에 답변하는 AI
AI Assistant: 사용자의 작업을 보조하는 AI
Second Brain: 사용자의 목표를 이해하고, 필요한 작업을 스스로 분해하여 Agent와 함께 수행하는 AI 업무 파트너
사용자가 "신규 쇼핑몰 서비스를 만들어줘"와 같이 목표를 전달하면, Supervisor Agent가 작업을 분석하고 필요한 Agent를 조율한다.

사용자 목표
    ↓
Supervisor Agent
    ↓
┌──────────────┐
│ Planning     │ → 기획 / 요구사항
│ Creative     │ → 디자인 / 이미지
│ Data         │ → 자료수집 / 분석
│ Engineering  │ → Frontend / Backend
│ AI           │ → ML / DL / LLM
│ Reflection   │ → 검증 / 개선
└──────────────┘
    ↓
결과물 생성
    ↓
사용자에게 제공
핵심 가치는 "답변"이 아니라 "업무 수행과 결과물 생성"에 있다.
서비스의 정체성은 계속 "개인 AI 업무 파트너 Agent 플랫폼"

정리.
Second Brain = 서비스
개인 AI 업무 파트너 = 핵심 가치
Supervisor + 6개 Worker Agent = 서비스 구조
Chatbot → Assistant → Worker = AI 서비스의 발전 방향

8. Agent별 역할
① Supervisor Agent — 조율
역할: 사용자 요청 분석, Task Decomposition, Agent 선택, Agent 실행 순서 관리, Agent 간 작업 조율, 결과 통합, 최종 결과 검토
기술: LLM, Prompt Engineering, LangGraph, ReAct, A2A, MCP

② Planning Agent — 기획
역할: 서비스 기획, 요구사항 정의, User Flow, 기능 명세, 일정/우선순위, PRD 및 기획서 생성
기술: LLM, Prompt Engineering, NLP, RAG, LangChain, T5

③ Creative Agent — 디자인
역할: UX/UI 설계, Wireframe, 디자인 방향, 이미지 생성, 디자인 개선, 브랜드 및 콘텐츠 생성
기술: Multimodal AI, Image Generation, Image Captioning, CNN, GAN, DALL·E

④ Engineering Agent — 개발
역할: 서비스 구조 설계, Frontend 개발, Backend 개발, API 설계 및 구현, Database 연동, 파일 처리, 기능 수정 및 개선
하위 역할: Frontend, Backend
기술: Python, Django, Django ORM, REST API, MySQL, HTML, CSS, JavaScript, Bootstrap, Frontend Architecture

⑤ Data Agent — 데이터
역할: Web Crawling, 데이터 수집, 데이터 전처리, SQL, ETL, 데이터 분석, 데이터 시각화
기술: Python, Web Crawling, SQL, MySQL, Pandas, NumPy, Matplotlib, Seaborn

⑥ AI Agent — AI 연구/개발
역할: ML 모델, DL 모델, NLP, LLM, Fine-tuning, 모델 학습, 모델 검증 및 평가, AI 기능 구현
기술: Machine Learning, Deep Learning, NLP, LLM, PyTorch, TensorFlow, Qwen, T5, PEFT, LoRA, QLoRA, Model Evaluation

⑦ Reflection Agent — 검증/개선
역할: AI가 만든 결과를 다시 평가, 결과 검증, 품질 평가, 오류 탐지, 요구사항 충족 여부 확인, 개선안 생성, 재작업 요청, 실행 결과 및 Report 생성
기술: LLM Judge, Evaluation Framework, RAG, Vector DB, Data Analysis, Report Generation

화면 Description:
관리자가 전체 프로젝트에서 생성된 결과물과 프로젝트별 Knowledge, Memory, Document, Template 및 Vector DB / RAG 상태를 통합적으로 관리하는 화면이다.
프로젝트를 선택하지 않은 경우 전체 프로젝트의 결과물과 Knowledge / RAG 현황 및 검색 성능 통계를 조회할 수 있으며, 특정 프로젝트를 선택하면 해당 프로젝트의 파일 구조와 Knowledge / RAG 데이터 및 성능 지표를 기준으로 화면이 전환된다.
결과물은 프로젝트별 폴더 구조로 탐색할 수 있으며, 파일을 선택하면 우측 Document Viewer에서 내용을 확인할 수 있다. 결과물은 공유 및 개별 다운로드가 가능하며, 프로젝트 단위의 결과물은 ZIP 파일로 다운로드할 수 있다.
문서 업로드는 현재 화면을 유지한 상태에서 업로드 모달(Popup) 을 통해 수행하며, 업로드된 문서는 선택된 프로젝트에 등록되고 이후 시스템에서 Chunking, Embedding 및 Vector DB Indexing 과정을 자동으로 수행한다.

10-9. 부가 UX 및 정책 안내 — 최신 화면 기준

사용자 가이드
사이드바 하단 사용자 전용 메뉴. PDF 내장 Viewer / 새 탭 / 다운로드 / 화면 둘러보기 제공.
현재는 샘플 PDF이며 실제 화면을 넣은 정식 PDF는 별도 제작한다.
PDF가 없으면 링크를 숨기고 준비 중으로 표시해야 한다. 현재 전용 페이지는 정적 PDF 링크이므로 파일 누락 시 안전 처리는 후속 보완 사항이다.

화면 Tour
상단 나침반 또는 가이드 페이지에서 수동 시작. Demo 로그인 자동 시작은 구현하지 않았다.
사용자: Dashboard → 프로젝트 목록 → 접근 가능한 프로젝트 결과물 → Coming Soon 목록 → 사용자 가이드.
관리자: Tasks → Agents → Coming Soon 목록 → 사용자 가이드 (현행 코드 경로).
현재 Coming Soon 강조 대상은 Hero가 아닌 기능 미리보기 목록이다.
이전·다음·완료·종료, Escape, 페이지 이동 후 이어보기 지원. 종료해도 서비스 이용 가능.
후속 보완: 관리자 Tour 마지막 사용자 가이드 단계를 관리자 초대 안내로 교체하고, Chat·알림 설명 단계를 별도로 검토한다.

사용자 초대
관리자 하단 버튼 → Modal. 대상 이메일(선택), 서비스 로그인 링크, 샘플 가이드 PDF, 안내문 표시.
링크·안내문 복사, 이메일 앱 열기(mailto), 브라우저 공유 지원. 공유 미지원 시 안내문 복사로 대체.
복사 권한이 없으면 직접 복사할 수 있게 내용을 선택하고 안내한다.
현재는 기존 로그인 URL 공유이며 초대 토큰·계정 생성·권한 부여·이메일 서버 발송은 없다.
대상 이메일은 저장하지 않으며, localhost 링크는 다른 기기용 초대 URL이 아님을 안내한다.
실제 초대 서비스는 만료·1회 사용·권한 검증·토큰 해시 저장 설계를 별도 확정한 뒤 구현한다.

FAQ · 이용 안내
사용자 메뉴 Projects 아래에 배치한다. AI 사용 안내는 PDF 내부나 화면 맨 아래에 숨기지 않고 페이지 상단에 표시한다.
제한 대상: 음란물, 폭력 조장 및 위해, 불법 행위 실행 지원, 명백한 위험 행위 지원.
AI 결과의 오류 가능성과 민감정보 입력 주의도 함께 안내한다.
하단 질문: 시작 방법 / 가이드 위치 / Google 임시 로그인 / 실행 제어 미연동 / 결과물 위치.
이 페이지는 정책 안내이며 실제 LLM Safety Filter가 작동한다는 의미가 아니다.
정책 변경 시 FAQ 텍스트와 운영 정책을 함께 검토한다. 실제 필터·Prompt 적용은 별도 Backend 작업이다.

사용자 경고 / 재생성 (회의 작업 25)
독립적인 사용자 제재 시스템이 아니다. Reflection 결과에서 재생성할 때의 확인 UI를 의미한다.
버튼: 처음부터 다시 만들기
확인: “현재 결과를 기반으로 처음부터 다시 작업하시겠습니까?”
경고: “기존 결과가 새로운 실행 결과로 대체될 수 있습니다.”
취소 / 다시 만들기 및 개선 의견 입력 제공. 현재 확인 이후에는 화면 상태만 바꾸며 재실행 API는 호출하지 않는다.
실제 연결 시 기존 Artifact 버전을 보존하고 새 실행 결과를 별도 버전으로 추가한다.

요청 실패 시 기존 결과를 유지하고 오류를 표시한다. 같은 요청의 중복 전송은 idempotency_key로 방지한다.

14-3. 공통 데이터·API 계약
실제 시간은 UTC timestamp로 저장하고 화면에서는 사용자 시간대 및 상대시간으로 표시한다.
PROJECT.updated_at은 프로젝트 정보나 작업·결과의 의미 있는 갱신 시 변경한다. 단순 조회로 변경하지 않는다.
Task / Run / Execution 상태: queued → running → succeeded / failed / cancelled.
중단 요청 시 running → cancel_requested → cancelled. 성공 완료가 먼저 확정되면 succeeded를 보존한다.
기존 Mock의 ready / todo / done 표시는 Adapter에서 대기 / 완료로 매핑하며 저장 상태를 뒤섞지 않는다.
모든 목록·상세·복사 가능한 파일 링크는 사용자 접근 권한을 검증한다.
서버 검색은 권한 범위 내에서만 동작하고 기존 화면 필터를 재사용한다.
Token 사용량 미수집은 null로 표현한다. 실제 0과 구분하며 Total은 수집된 Input + Output에서 계산한다.
동일 실행의 LLM 호출·재시도는 별도 사용량 행으로 기록하고 provider 요청 식별자로 중복 집계를 막는다.
Timeline과 Activity Log는 같은 이벤트 원본을 사용하며 Pipeline 상태는 실행 데이터에서 파생한다.
Reflection의 기준점수·산출점수·차이·감점 항목은 평가 당시 기준 snapshot으로 고정한다.
가중치 합계 정책은 활성 기준을 100으로 검증하고 비활성 기준은 평가·합계에서 제외한다.
INSTRUCTION은 공통(프로젝트 없음) / 프로젝트별로 구분한다. 충돌 시 프로젝트별 지시를 우선하되 안전 정책은 우회할 수 없다.
알림과 오류 Header는 같은 오류 이벤트를 참조하되, Header 닫기는 작업 성공이나 알림 읽음으로 처리하지 않는다.

14-4. 완료·검증 기준
UI: 일반 / Demo / 관리자별 메뉴, 접기·펼치기, Popup 취소·확인, 모바일 배치, 키보드 접근 확인.
기능 연결: 권한 없는 조회 차단, 실패·빈 데이터·미계측 상태, 재시도·중복 클릭 검증.
중단: Worker 종료 확인, 진행 중 결과의 처리 방침, 중단 이후 추가 실행 방지 검증.
재생성: 취소 시 변화 없음, 확인 시 새 실행 1회, 기존 결과 보존, 새 버전 조회 검증.
문서·DB 설계·API 응답·화면 의미가 일치한 경우에만 실제 기능 완료로 기록한다.

15. 전체 점검 결과 및 보완 기준 (2026-10-20)

15-1. 전체 점검 요약
현재 기획안은 문제 정의, 사용자 흐름, 화면 스토리보드, UI와 실제 Backend 기능의 구분, DB 확장 설계, 권한·상태·이력 관련 기준까지 구체적으로 정리되어 있다. 특히 14장의 작업별 미연동 상태와 DBML의 버전·소유권·멱등성 규칙은 Backend 구현의 기준으로 유지한다.
반면 ① MVP의 완료 조건과 후속 기능의 경계가 여러 장에 흩어져 있고, ② 실행 단계별 선행조건·산출물·검증 책임이 일정으로 연결되지 않으며, ③ Agent 오류·재시도·비용·운영 전환의 공통 기준이 부족하다. 이를 보완하기 위해 15-2의 MVP 게이트와 16장의 20일 실행 계획을 추가한다.

15-2. MVP 범위 및 완료 게이트
MVP 목표는 “사용자가 프로젝트에서 요청을 보내면 Supervisor가 작업을 만들고 Planning이 PRD를 생성하며 Reflection이 기준에 따라 평가하고, 사용자가 버전이 보존된 결과를 확인하는 한 번의 종단 간 흐름”이다.
필수 범위: USER / PROJECT 소유권 검사와 프로젝트 저장, Conversation / Message 저장, 실행 요청 중복 방지, Supervisor의 최소 작업 분해, Planning 결과 생성, Reflection 결과 및 평가 기준 snapshot 저장, Run / Task / Execution 이벤트와 Artifact 버전 연결, 진행·완료·실패 화면 표시, 실패한 실행의 기존 결과 보존.
MVP 완료 판정은 한 개의 실제 사용자 시나리오가 새 프로젝트부터 최종 결과 확인까지 이어지고, 권한 없는 접근이 차단되며, 실패·재시도·중복 요청에서도 기존 Artifact가 손상되지 않는 것을 기준으로 한다. 화면 샘플이나 고정 Mock 점수만 표시되는 것은 완료로 세지 않는다.
MVP 후속 범위: Creative / Engineering / Data / AI Worker 확대, 고급 RAG·Memory, MCP·A2A, 실제 Google OAuth 및 관리자 Face 인증, 메일 초대, 고급 Safety Filter, 범용 전역 검색, 자동 배포. MVP 일정이 남고 필수 게이트를 통과한 경우에만 선택한다.

15-3. 완료 프로젝트(Sbrain-git)에서 반영한 실행 원칙
① Agent와 Orchestrator의 책임을 구분한다. Agent는 결과 내용을 만들고, Orchestrator는 실행 순서, 입력·출력 계약, 상태, 재시도, 재개, 중단, 이력, 사용자 대기 지점을 관리한다.
② 각 Agent 단계의 입출력 필드, 필수값, 버전, 실패 형식, 파일 참조 방식을 사전에 계약으로 고정한다. 외부 API·Worker 연결은 문서화된 API 계약과 계약 검증을 통과해야 활성화한다.
③ 일시적 호출 실패 재시도, 사용자가 요청하는 재작성, 시스템이 품질 검사 후 수행하는 재수행을 서로 다른 동작으로 정의한다. 최대 횟수·대기 간격·최종 실패 상태·사용자 안내를 설정으로 관리하고, 무한 재실행을 허용하지 않는다.
④ 최소 실행 경로를 먼저 연결한 뒤 Worker를 한 종류씩 추가한다. 각 단계가 독립 실행 가능하도록 Stub / 실제 연결을 명시하고, Stub 결과를 실제 기능 완료로 표시하지 않는다.
⑤ 흐름 시험은 실제 외부 LLM 호출과 분리하고 기본은 가짜 호출처·고정 입력을 사용한다. 외부 호출 시험은 별도 실행으로 분리해 API 비용·사용량·로그를 확인한다.
⑥ 외부 호출별 입력·출력 Token, 모델, 소요 시간, 재시도, 성공·실패 사유를 실행에 연결한다. 사용량을 알 수 없는 값은 0 대신 미계측(null)로 표시한다. 일별·실행별 호출 상한과 비용 중단 기준을 배포 전 정한다.
⑦ 실행 로그·산출물·사용자 대화의 보존 기간, 완전 삭제 범위, 백업과 복구 절차를 정한다. 비밀키는 저장소·프론트엔드·일반 로그에 두지 않고 서버 환경 설정으로 주입한다. 파일과 검색은 프로젝트 소유권을 매 요청마다 확인한다.
⑧ DB 변경은 nullable 확장 → 데이터 보정 → 검증 → 제약 강화 순서로 계획하고, 적용 전 백업·복구 경로를 마련한다. 기획 문서의 DBML은 설계안이며 운영 DB 적용 완료를 뜻하지 않는다.
⑨ Git 이슈·작업 단위를 작게 나누고 기능별 완료 시 변경을 검토한다. main 직접 변경보다 기능 브랜치·리뷰·자동 검증을 기본으로 하되, 개인 프로젝트에서는 최소한 커밋 단위와 변경 기록을 유지한다.

15-4. 선행 결정이 필요한 운영값
다음 값은 구현 시작 전에 결정하고 환경별 설정으로 관리한다: 배포 환경·도메인·HTTPS, DB와 파일 저장소, 인증 공급자와 Demo 제한, 업로드 파일 형식·최대 크기·보존 기간, 동시 실행 수, 단계별 시간 제한·재시도 상한, LLM 모델·호출 상한·월 예산, 오류 알림 수신자와 로그 보존 기간.
값이 정해지기 전에는 안전한 로컬 기본값과 Stub로 개발하되, 임시 값이 운영값으로 오인되지 않도록 설정표에 상태(미정 / 개발 / 운영)를 표시한다.

17. React Frontend 전환 계획 및 진행 상태 (2026-10-20)

17-1. 기술 선택
화면 계층은 React 19 + TypeScript + Vite를 사용한다. 서버 측 로그인·권한·기존 기능은 Django가 유지하고, 기존 URL을 보존하면서 화면 계층을 React로 전환한다. Django 템플릿 전체를 한 번에 제거하지 않고, 각 URL의 React 전환·권한·기능 검증 후 미사용 템플릿을 정리한다.
라우팅은 React Router, 서버 데이터 요청·캐시는 TanStack Query, 화면 전용 전역 상태는 Zustand, 폼은 React Hook Form + Zod를 사용한다. 스타일은 Tailwind CSS 4를 기준으로 하며 shadcn/ui 패턴의 컴포넌트를 저장소에 복사해 제품 색상·접근성에 맞게 관리한다. Radix UI primitives, class-variance-authority, clsx, tailwind-merge, lucide-react는 공통 UI 구성에 사용한다.
Mantine / Ant Design / Redux Toolkit / Jotai / TanStack Router는 현재 MVP에 함께 넣지 않는다. 중복 UI·상태 계층을 피하고 필요성이 확인되면 별도 비교 후 선택한다. Next.js는 Django가 이미 Backend와 세션 인증을 담당하므로 지금 범위에는 도입하지 않는다.

17-2. Django 연동 원칙
Django는 인증·세션·권한·도메인 API·파일 권한을 계속 책임진다. 현재 화면은 Django view가 만든 페이지별 초기 JSON payload를 `json_script`로 전달받고, 일부 동작만 기존 Django 경로에 요청한다. 향후 데이터 갱신은 명시적인 API 응답으로 연결하며 React는 DB나 비밀값에 직접 접근하지 않는다.
정적 빌드는 `front/react`에서 생성하고 Django `static/react`가 배포 asset을 제공한다. Vite manifest에서 entry 및 CSS 파일을 읽어 얇은 HTML mount template에 연결한다. React Router는 공통 Provider와 향후 화면 전환에 쓰며, 기존 Django URL의 세션·권한·페이지별 데이터 전달을 유지하기 위해 현재 페이지 navigation은 서버 URL을 따른다. 새 URL을 추가할 때 Django 경로와 React 화면 매핑을 함께 갱신한다.
개발 시 Vite 개발 서버는 127.0.0.1:5173에서 실행한다. Django 세션이 필요한 API는 CSRF 및 same-origin 또는 명시된 개발 proxy 정책을 따른다. 운영 배포에서는 빌드 산출물만 제공하고 개발 서버는 외부에 공개하지 않는다.
기존 페이지 CSS와 이미지 자산은 시각적 연속성을 위해 재사용한다. 기존 Bootstrap 기반 페이지 동작은 React로 옮기되, 화면 둘러보기와 프로젝트 채팅처럼 남아 있는 스크립트는 React mount 이후 초기화하는 임시 연결로 한정한다. React와 기존 스크립트가 같은 동작을 중복 처리하지 않도록 이벤트 소유자를 정하고, 미사용 템플릿·CSS·JS는 참조 여부와 기능 동등성을 확인한 후 정리한다.

17-3. 전체 화면 React 전환 기록
전환 완료: Dashboard, 로그인·Demo·Face 인증, Projects 목록·생성·상세·Chat, 전체 프로젝트, 관리자 Tasks·Agents·Agent 상세·Results/Knowledge, FAQ·사용자 가이드, Coming Soon 목록·상세·관리·편집, 권한 안내 화면의 콘텐츠와 로그인 이후 공통 헤더·사이드바를 React에서 렌더링한다. 로그인 화면은 별도 React mount를 쓴다. 얇은 Django mount template은 CSRF 토큰·초기 JSON·정적 bundle만 제공한다.
추가된 기반: React Router와 TanStack Query Provider, Tailwind CSS, shadcn/ui 패턴의 Button/Card, React 폼·Markdown preview·공통 navigation/modal, Vite manifest 기반 asset 연결. 화면 데이터는 안전한 `json_script` 초기 payload로 넘기며, 관리자 권한 및 로그인 검사는 기존 Django view decorator에서 유지한다.
기능 경계: Django는 세션 인증, 권한, 데이터 조회, 필터 요청, Coming Soon 파일 저장·삭제, 프로젝트 Chat Stub 응답을 계속 처리한다. 화면 이동은 Django URL로 페이지별 권한 검사와 데이터 payload를 다시 받는다. 다크 테마와 모바일 메뉴는 React shell에서 처리하며, 화면 둘러보기는 기존 안내 스크립트를 연결한다.
검증 현황 (2026-10-20): `npm run build`, `tsc --noEmit`, `manage.py check`, `manage.py test apps`(12건)가 통과했다. 로그인 사용자·관리자 세션으로 주요 경로 15개가 HTTP 200, React mount root와 빌드 bundle 참조를 반환하는 것을 Django Client로 확인했다. 원본 GIF·로고·로딩 이미지 파일 존재도 확인했다. 이는 브라우저 렌더링과 반응형 시각 비교를 완료했다는 뜻은 아니다. 기존 문서의 Dashboard 1개·테스트 11건 기록은 전체 페이지 전환 전의 과거 기록이므로 현 상태 설명으로 사용하지 않는다.
화면 회귀 보완 (2026-10-20): React 전용 전역 링크 규칙이 원본 Bootstrap 링크 색을 덮던 문제를 제거했다. Dashboard의 원본 GIF 배경과 Brain 궤도 장식을 유지하고, 공통 CSS·페이지별 원본 CSS 및 기존 이미지 경로를 mount template에 연결했다. React가 생성한 화면 뒤에 공통 스크립트가 초기화되도록 mount 이벤트를 추가했으며 사이드바는 React가 단독 제어하고 채팅 스크립트는 화면 전환 후 초기화하도록 했다. 브라우저 캡처 도구가 실행 환경 경로 오류로 시작되지 않아 실제 화면 캡처 기반의 원본 대비 픽셀 검수는 남아 있다.
화면 안내·접근 제한 보완 (2026-10-20): 화면 둘러보기 진행 상태는 브라우저 저장소 권한에 의존하지 않고 URL fragment로 다음 화면에 전달한다. 관리자 전용 화면 안내에는 Dashboard·프로젝트·Coming Soon으로 가는 실제 링크를 제공한다. Dashboard Hero 장식은 넓은 화면에서 오른쪽 끝에 배치한다.
2026-10-20 React 전환 당시의 실제 동작 한계: 프로젝트·Task·Agent 화면 데이터는 대부분 `apps/mockdata.py` 기반이고 실제 Agent 실행·Google/Face 인증·초대 메일 발송·알림은 시연/Stub이었다. 프로젝트 생성은 저장소 연동 없이 기존처럼 목록으로 돌아갔다. UI가 React로 전환된 사실은 Backend 기능 완료나 DB/API 실연동을 뜻하지 않는다.
후속 Backend 연결 기록 (2026-10-26, Reflection 보완 전): Day 5–20 작업으로 Project/Conversation/Message 저장, 사용자 소유권, Run/Task/AgentExecution, Planning Artifact, Reflection 보고서, 이벤트·재시도·취소·재생성 API를 연결했다. Planning은 로컬 Ollama `gemma4:latest`를 기본 provider로 사용하고 외부 hosted API는 연결하지 않는다. 당시 Reflection은 규칙 기반 Mock이었고 브라우저 실화면/좁은 화면 QA도 남아 있었다. 실제 Face/OAuth, 초대 메일, 알림 연동, 다른 Worker, 운영 DB·worker·백업 구성은 별도 미완료다. 최신 검증과 제한은 `기획/6. 테스트 및 보완.txt`를 기준으로 한다.
Reflection 보완 기록 (2026-10-26): 위 후속 기록 이후 `apps/reflection/evaluator.py`를 로컬 Ollama 평가로 교체했다. Artifact와 가중 기준 snapshot을 전달하고 기준별 key·0–100 점수·근거·개선 제안 형식을 검증한다. 모델 미설치·서비스 오류·잘못된 응답은 오류 처리하며 mock 점수로 대체하지 않는다. 프로젝트 상세에는 평가 요청 버튼, 점수·근거·감점·개선 제안 표시를 연결했다. Planning 및 Reflection의 live Ollama 종단 테스트가 통과했다. 브라우저 실제 렌더/클릭 QA는 아직 남아 있다. 최신 검증 결과는 `기획/6. 테스트 및 보완.txt`에서 갱신한다.
커밋 기능 점검에서 확인·수정: 이전 SmokeTest가 현재 존재하지 않는 `mcp-tool-extension` 문서를 참조하던 부분을 실제 `daily-briefing`으로 맞췄다. `sample.md`에 YAML front matter가 없어 사용자 목록에서 누락되던 문제를 수정했다. 17-4. React 작업 실행 방법
초기 설치: `cd front/react` 후 `npm install`.
개발 서버: `npm run dev` (Vite 127.0.0.1:5173). Django 개발 서버와 함께 사용한다.
배포용 asset 생성: `npm run build`. 생성물은 `front/static/react/`이며 빌드 manifest를 포함한다. Django에서 새 asset을 제공하려면 React build 후 Django를 실행한다.
현재 Node 20.17 환경을 위해 Vite 6.4.1 및 `@vitejs/plugin-react` 4.x를 고정 범위로 사용한다. Node 최소 요구 버전이 바뀌면 Vite 업그레이드 전에 개발 환경을 함께 조정한다.
